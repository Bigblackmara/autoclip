# Live Watch — implementation plan

## Problem statement

AutoClip has a fast, quality pipeline for *long* videos: ingest → prepare →
transcribe → highlights → reframe → captions → export. The user wants an
additive feature that runs the same quality stages against *live* streams:

    watch N streams 24/7 → detect the viral moment the second it happens →
    clip with pre/post-roll → captions + 9:16 reframe → optional upload.

Additive-only: `autoclip clip`, `autoclip serve`, the review UI, and all
existing tests must be untouched in behavior. All new surface area hides
under `backend/autoclip/live/`, `api/live.py`, new CLI subcommands, and new
frontend routes — nothing existing is edited except additive hooks (config
schema additions, one main.tsx route addition, App nav link, api/__init__
router wiring).

## Architecture (target)

```
                    FastAPI (existing, one process)
                      └─ api/live.py (new router; A10)
                          └─ LiveManager (live/manager.py; A8)
                                ├─ per-stream Watcher tasks (A8)
                                │     ├─ Capture (capture.py; A1)
                                │     │    └─ RingBuffer (buffer.py; A1)
                                │     ├─ AudioSignalWorker (A2)
                                │     └─ ChatSignalWorker (A5, Twitch IRC)
                                ├─ Detector: SignalAggregator+Trigger (A4)
                                │    └─ Circuit: cooldown + LLM token buckets (A4)
                                ├─ Judge (LLM gate; A6)
                                └─ ClipFactory (A8→A8b)
                                     └─ existing pipeline stages (reused)
                                          └─ uploaders (A7): YouTube/Instagram
```

Key rule: **watchers are lightweight, heavy work is globally throttled.**
A watch is just streamlink → ffmpeg writing .ts segments + cheap numpy
analysis. The heavy GPU/CPU work (transcribe, reframe, encode) runs through a
global bounded queue with 1 worker default (matching JobQueue's "GPU wants the
whole machine" philosophy). One stream crashing must never affect others:
each watcher is its own asyncio task with its own subprocess, strict error
containment, and a supervisor loop that reconnects with exponential backoff.

## Test strategy

- Unit tests, per-module, written by each worker next to their module in
  tests/test_live_*.py (names reserved below).
- Slower integration tests gated with pytest markers like the existing suite
  (a new `live` marker for tests needing a real fake live source over RTMP
  or a file-loop; ran only in my final verification).
- Existing suite must stay green: `pytest -m "not slow and not golden and not e2e"`
  must remain 276 passed, plus every new test file.
- The full E2E at the end: a real ffmpeg HLS/WTNV push into a local nginx
  (docker) or file-loop capture via a custom streamlink plugin; detection →
  clip render with captions; asserted on disk artifacts + DB rows + SSE events.

## House style (from CONTRIBUTING + code)

- ruff line length 100, target py311; `ruff check` + `ruff format --check` clean.
- Docstrings: module purpose first, "why" not "what", real failure stories.
- No new runtime deps beyond `[live]` extra (streamlink). WebSocket client
  comes transitively via streamlink; do not add explicit deps.
- SQLite: raw sqlite3, per-thread connections, WAL. No ORM.
- Pydantic at the API boundary only; dataclasses for rows.
- Tests: same style as existing suite (class-per-concern, descriptive names).

## Marker registration

pyproject adds: `live: tests that need a running fake live source or streamlink`

## Legal notice (spec hard rule)

docs/LIVE_WATCH.md carries a visible notice: the user is responsible for
having the rights/permission to clip and repost each streamer's content and
for following each platform's ToS. The GUI (F1) shows the same notice. Upload
subsystem (A7) refuses to run when no rights attestation checkbox was ever
accepted in the UI (stored in config).

## Out of scope (v1, documented as ASSUMPTION)

- Kick chat (no public chat API; streamlink capture works for Kick video).
- YouTube Live chat (quota/permission heavy; capture works for video).
- Visual-only signals (scene-cut detection on live H.264 is noisy and costly).
- Reframe tracking quality work (reuses existing reframe stage as-is).
- Auto-publish beyond one manual/auto attempt per platform per clip.

## Decisions during the build

- **The LLM judge runs on an API provider, not Ollama** (user decision,
  mid-build): detection quality follows model quality, and the 8 GB GPU is
  better spent on Whisper/MediaPipe/NVENC. judge.py builds the provider the
  standard way (providers.build_provider(active_provider, settings)) so the
  user picks it in Settings like everywhere else; hosted concurrency mirrors
  highlights.py (3 parallel judge calls, 1 if someone insists on Ollama).
  Local Ollama remains supported — it's just not the default recommendation.
